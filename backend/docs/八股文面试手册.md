## 一、Java 基础（1-20）

<details>
<summary>1. == 和 equals 的区别？★★★</summary>

- `==` 比较基本类型的值；引用类型比较的是内存地址。
- `equals` 默认就是 `==`（Object 实现），重写后才比较内容（如 String、包装类）。
- 坑：`Integer` 缓存 -128~127，超出范围 `==` 比较地址会 false。
</details>

<details>
<summary>2. 重写 equals 为什么必须重写 hashCode？★★★</summary>

- hashCode 契约：两个对象 equals 相等，hashCode 必须相等。
- HashMap/HashSet 先按 hashCode 找桶、再用 equals 精确比较。
- 只重写 equals 不重写 hashCode，会导致 equals 相等的对象被分到不同桶，get 不到、去重失效。
</details>

<details>
<summary>3. String / StringBuilder / StringBuffer 的区别？★★★</summary>

- String 不可变，拼接产生新对象，循环里 `+` 性能差。
- StringBuilder 可变、线程不安全，单线程最快。
- StringBuffer 可变、方法加 synchronized，线程安全，性能略低。
</details>

<details>
<summary>4. 重载和重写的区别？★★</summary>

- 重载：同类内方法名相同、参数列表不同，编译期决定调用哪个。
- 重写：子类覆盖父类方法，方法签名一致，运行期多态；不能缩小访问权限、不能抛出更宽异常。
</details>

<details>
<summary>5. 接口和抽象类怎么选？★★★</summary>

- 抽象类：可以有状态、构造器、已实现的方法；单继承。
- 接口：常量、抽象方法、default/static 方法；可多实现。
- 经验：优先接口；需要共享代码或状态时用抽象类。
</details>

<details>
<summary>6. 深拷贝和浅拷贝的区别？★★</summary>

- 浅拷贝：引用字段只复制引用，新旧对象共享同一个引用对象。
- 深拷贝：引用字段也复制出新的对象。实现：重写 clone 逐层拷贝、序列化、手动 new。
</details>

<details>
<summary>7. final 关键字的作用？★★</summary>

- 修饰类：不可继承；修饰方法：不可重写；修饰变量：引用不可变（对象内容可变）。
- final 字段必须在构造完成前赋值。
</details>

<details>
<summary>8. static 关键字的作用？★★</summary>

- 静态变量/方法属于类，不依赖实例；静态代码块在类加载时执行。
- 静态方法不能访问实例成员；静态成员多线程共享。
</details>

<details>
<summary>9. Java 异常体系？★★★</summary>

- Throwable 下分 Error（JVM 问题，不处理）和 Exception。
- Exception 分 checked（编译期必须处理，如 IOException）和 unchecked（RuntimeException，可不声明）。
- 常见 RuntimeException：NPE、ClassCastException、IndexOutOfBounds、IllegalArgumentException。
</details>

<details>
<summary>10. 反射是什么？常用 API 和代价？★★</summary>

- 运行时获取类的结构（字段/方法/注解）并动态调用。
- 常用：Class.forName、getMethod、getDeclaredField、setAccessible、invoke。
- 用途：Spring IOC/AOP、框架；代价：性能低、破坏封装。
</details>

<details>
<summary>11. 泛型是怎么实现的？★★</summary>

- 类型擦除：编译后泛型信息被擦除，运行时是 Object 或边界类型。
- 泛型只在编译期做类型检查，运行时靠强转。
- 限制：不能 new T()、不能 T.class、基本类型不能做泛型参数。
</details>

<details>
<summary>12. 自动装箱/拆箱有哪些坑？★★</summary>

- Integer.valueOf 缓存 -128~127，超出范围 == 比较的是地址。
- 拆箱时对象为 null 会 NPE。
</details>

<details>
<summary>13. 面向对象三大特性？★★★</summary>

- 封装：隐藏实现、暴露方法，保护内部状态。
- 继承：复用与 is-a 关系，Java 单继承。
- 多态：编译看左边、运行看右边；靠重写和向上转型实现。
</details>

<details>
<summary>14. Java 是值传递还是引用传递？★★★</summary>

- 都是值传递：基本类型传值，引用类型传「引用的副本」。
- 方法内改引用指向不影响外部；但通过引用改对象内容会影响外部。
</details>

<details>
<summary>15. try-with-resources 是什么？★★</summary>

- 自动关闭实现 AutoCloseable 的资源（流、连接、锁）。
- 比 finally 简洁；主异常 + 抑制异常（addSuppressed）机制。
</details>

<details>
<summary>16. Comparable 和 Comparator 的区别？★★</summary>

- Comparable：类自身实现 compareTo，内比较，只能一种排序。
- Comparator：外部比较器，可灵活定义多种规则，用于排序、TreeMap。
</details>

<details>
<summary>17. transient 关键字？★★</summary>

- 序列化时跳过该字段，不参与默认序列化。
- 可配合自定义 writeObject/readObject 手动处理。
</details>

<details>
<summary>18. Object 类有哪些常用方法？★</summary>

- equals、hashCode、toString、clone、getClass、wait、notify、notifyAll、finalize。
</details>

<details>
<summary>19. 内部类的种类？★</summary>

- 成员内部类、静态内部类、局部内部类、匿名内部类。
- 静态内部类不持有外部类引用，更省内存（如 HashMap.Node 就是静态的）。
</details>

<details>
<summary>20. 不可变类怎么设计？★★</summary>

- final 类、final 字段、不提供 setter、getter 返回拷贝或不可变集合。
- 例：String、Integer、BigDecimal；天然线程安全、可缓存。
</details>

## 二、集合（21-35）

<details>
<summary>21. ArrayList 和 LinkedList 的区别？★★★</summary>

- ArrayList：动态数组，随机访问 O(1)，尾部插入 O(1)、中间插入删除 O(n)，内存连续。
- LinkedList：双向链表，插入删除 O(1)（已知节点），随机访问 O(n)，节点开销大。
- 实际场景大部分用 ArrayList 更快。
</details>

<details>
<summary>22. ArrayList 扩容机制？★★★</summary>

- 默认容量 10（懒加载，首次 add 才分配）。
- 满时扩容 1.5 倍（old + old>>1），Arrays.copyOf 拷贝。
- 能预估容量就用 new ArrayList(capacity)，减少扩容。
</details>

<details>
<summary>23. HashMap 底层结构（JDK8）？★★★</summary>

- 数组 + 链表 + 红黑树。
- 链表长度 ≥8 且数组长度 ≥64 树化；长度 <6 退化为链表。
- 默认容量 16、负载因子 0.75、扩容翻倍。
</details>

<details>
<summary>24. HashMap put 流程？★★★</summary>

- hash = key.hashCode 高低位异或 → 定位桶。
- 桶空直接放 Node；桶非空：key 相同则覆盖，红黑树走树插入，否则链表尾插（JDK8），到阈值树化。
- 元素数 > 容量×0.75 时扩容。
</details>

<details>
<summary>25. HashMap 为什么线程不安全？★★</summary>

- JDK7：头插法，并发扩容可能成环（死循环）。
- JDK8：尾插避免成环，但并发 put 会互相覆盖、size 不准。
- 并发场景用 ConcurrentHashMap。
</details>

<details>
<summary>26. ConcurrentHashMap 如何保证线程安全？★★★</summary>

- JDK7：分段锁（Segment 继承 ReentrantLock）。
- JDK8：CAS + synchronized 锁桶头节点；扩容时其他线程协助迁移（ForwardingNode）。
- 读无锁（节点 volatile），size 用 baseCount + CounterCell 累加。
</details>

<details>
<summary>27. HashMap 容量为什么是 2 的幂？★★</summary>

- 取模优化：hash & (n-1) 等价于 hash % n，位运算更快。
- 扩容时元素要么原位、要么 +oldCap，迁移高效。
</details>

<details>
<summary>28. 负载因子为什么默认 0.75？★★</summary>

- 空间/时间权衡：太小浪费内存，太大冲突变多。
- 0.75 下泊松分布桶内链表很短，这也是树化阈值取 8 的由来。
</details>

<details>
<summary>29. HashSet 底层实现？★</summary>

- 基于 HashMap，value 是固定 PRESENT 对象。
- 去重依赖 key 的 hashCode + equals。
</details>

<details>
<summary>30. TreeMap/TreeSet 底层？★★</summary>

- 红黑树（自平衡二叉查找树），操作 O(log n)。
- 天然有序，可传 Comparator 自定义排序。
</details>

<details>
<summary>31. LinkedHashMap 有什么用？★★</summary>

- 额外用链表维护插入顺序；accessOrder=true 时按访问序排列。
- 重写 removeEldestEntry 可实现 LRU 缓存。
</details>

<details>
<summary>32. fail-fast 是什么？★★</summary>

- 迭代遍历时结构被修改（modCount 变化）抛 ConcurrentModificationException。
- 不是绝对保证；CopyOnWriteArrayList 的迭代器是弱一致的，不抛。
</details>

<details>
<summary>33. 有哪些线程安全的集合？★★</summary>

- 旧：Vector、Hashtable、Collections.synchronizedXxx（全表锁，性能差）。
- 新：ConcurrentHashMap、CopyOnWriteArrayList/Set、BlockingQueue 系列、ConcurrentSkipListMap。
</details>

<details>
<summary>34. Queue/Deque 常用实现？★</summary>

- ArrayDeque：循环数组，可做栈/队列，不能存 null。
- 阻塞队列：ArrayBlockingQueue（有界）、LinkedBlockingQueue（默认无界）、SynchronousQueue（不存元素）。
</details>

<details>
<summary>35. Collections/Arrays 常用方法？★</summary>

- Collections：sort、reverse、binarySearch、unmodifiableXxx、singletonList。
- Arrays：asList（注意返回固定长度列表）、copyOf、fill、sort。
</details>

## 三、JVM（36-50）

<details>
<summary>36. JVM 运行时内存区域？★★★</summary>

- 线程私有：程序计数器、虚拟机栈、本地方法栈。
- 线程共享：堆（对象）、方法区（类信息、常量、静态变量）。
- JDK8+ 方法区实现为元空间（本地内存），不再有永久代。
</details>

<details>
<summary>37. 堆内存怎么划分？★★★</summary>

- 新生代：Eden + 两个 Survivor（S0/S1，默认 8:1:1），新对象优先放 Eden。
- 老年代：大对象、长期存活对象。
- Minor GC（新生代，复制算法）、Major/Full GC（老年代/整堆）。
</details>

<details>
<summary>38. 对象创建过程？★★</summary>

- 类加载检查 → 分配内存（指针碰撞/空闲列表）→ 初始化零值 → 设置对象头 → 执行构造方法。
</details>

<details>
<summary>39. 类加载过程？★★★</summary>

- 加载（读字节码）→ 验证 → 准备（静态变量赋默认值）→ 解析（符号引用转直接引用）→ 初始化（静态块/静态变量赋值）。
</details>

<details>
<summary>40. 双亲委派机制？★★★</summary>

- 类加载请求先交给父加载器，父加载不了才自己加载。
- 好处：避免类重复加载、防止核心类被篡改（如自定义 java.lang.String）。
- 打破场景：SPI（ServiceLoader）、Tomcat 应用隔离、JDK9 模块化。
</details>

<details>
<summary>41. 如何判断对象可回收？★★★</summary>

- 可达性分析：从 GC Roots（栈引用、静态变量、常量、JNI 引用）出发，不可达即垃圾。
- 不用引用计数法（循环引用问题）。
- finalize 不推荐；可用虚引用做资源清理。
</details>

<details>
<summary>42. 垃圾回收算法？★★★</summary>

- 标记-清除：快但有内存碎片。
- 标记-复制：新生代用，无碎片，浪费空间（靠 S0/S1 优化）。
- 标记-整理：老年代用，无碎片，但移动对象慢。
</details>

<details>
<summary>43. 常见垃圾收集器？★★★</summary>

- CMS：并发标记清除，低停顿，有碎片和浮动垃圾，JDK14 移除。
- G1：Region 分区，可预测停顿，JDK9+ 默认。
- ZGC：染色指针，停顿毫秒级，适合超大堆。
</details>

<details>
<summary>44. 内存泄漏常见场景？★★★</summary>

- 静态集合持有对象、ThreadLocal 不 remove、流/连接未关闭、监听器未注销、缓存无淘汰策略。
</details>

<details>
<summary>45. 常见 OOM 类型？★★</summary>

- 堆溢出（对象太多）、栈溢出（递归过深 StackOverflowError）、元空间溢出（动态生成类太多）、直接内存溢出。
</details>

<details>
<summary>46. 常用 JVM 调优参数？★★</summary>

- -Xms/-Xmx 堆大小、-Xmn 新生代、-XX:MetaspaceSize、-XX:+UseG1GC、-Xlog:gc*、-XX:MaxDirectMemorySize。
</details>

<details>
<summary>47. 强/软/弱/虚引用区别？★★</summary>

- 强：不回收；软：内存不足才回收（适合缓存）；弱：下次 GC 就回收（ThreadLocal 的 key）；虚：配合队列跟踪对象回收。
</details>

<details>
<summary>48. 程序计数器为什么是线程私有的？★</summary>

- 记录当前线程执行的字节码行号，线程切换后才能恢复执行位置；执行 native 方法时为空。
</details>

<details>
<summary>49. 栈帧包含什么？★</summary>

- 局部变量表、操作数栈、动态链接、方法返回地址。
</details>

<details>
<summary>50. 对象的内存布局？★</summary>

- 对象头（Mark Word + 类型指针，数组还有长度）、实例数据、对齐填充。
</details>

## 四、并发（51-70）

<details>
<summary>51. 进程和线程的区别？★★★</summary>

- 进程：资源分配单位，独立地址空间，切换开销大。
- 线程：CPU 调度单位，共享进程资源（堆、方法区），有独立栈和程序计数器，切换开销小。
</details>

<details>
<summary>52. 创建线程的方式？★★</summary>

- 继承 Thread、实现 Runnable、实现 Callable（有返回值，配合 FutureTask）、线程池。
- 推荐线程池，避免频繁创建销毁线程。
</details>

<details>
<summary>53. 线程有哪些状态？★★★</summary>

- NEW → RUNNABLE →（BLOCKED / WAITING / TIMED_WAITING）→ TERMINATED。
- Java 的 RUNNABLE 包含操作系统的就绪和运行；synchronized 阻塞是 BLOCKED，Object.wait 是 WAITING。
</details>

<details>
<summary>54. sleep 和 wait 的区别？★★★</summary>

- sleep：Thread 静态方法，不释放锁，到点自动醒。
- wait：Object 方法，必须持有锁，会释放锁，需 notify/notifyAll 唤醒，可带超时。
</details>

<details>
<summary>55. synchronized 原理？★★★</summary>

- 基于 Monitor，字节码 monitorenter/monitorexit，可重入。
- JDK6 后锁升级：无锁 → 偏向锁 → 轻量级锁（自旋）→ 重量级锁（阻塞）。
- 锁的是对象：实例、类、代码块。
</details>

<details>
<summary>56. volatile 的作用和原理？★★★</summary>

- 可见性：写后立即刷主内存（内存屏障）。
- 有序性：禁止指令重排序（经典 DCL 单例）。
- 不保证原子性：i++ 仍然不安全。
</details>

<details>
<summary>57. volatile 和 synchronized 的区别？★★★</summary>

- volatile：轻量，只保证可见性+有序性，不能保证原子性。
- synchronized：保证原子性（互斥），也保证可见性。
- 单写多读用 volatile；读改写用锁或原子类。
</details>

<details>
<summary>58. CAS 是什么？ABA 问题？★★★</summary>

- 比较并交换：内存值等于期望值才更新，CPU 原子指令。
- ABA：A→B→A，CAS 误判没变过；解决：版本号（AtomicStampedReference）。
- 高竞争下自旋空转 CPU。
</details>

<details>
<summary>59. AQS 原理？★★★</summary>

- AbstractQueuedSynchronizer：state 状态 + CLH 双向等待队列。
- 独占（ReentrantLock）/共享（Semaphore、CountDownLatch）两种模式，模板方法 tryAcquire/tryRelease。
</details>

<details>
<summary>60. ReentrantLock 和 synchronized 的区别？★★★</summary>

- ReentrantLock：可中断、可超时、公平锁、多 Condition、需手动 unlock（finally 中释放）。
- synchronized：自动释放、不可中断、非公平。
</details>

<details>
<summary>61. 公平锁和非公平锁？★★</summary>

- 公平：按请求顺序（队列 FIFO）获得锁，性能略低。
- 非公平：允许插队，吞吐更高；ReentrantLock 默认非公平。
</details>

<details>
<summary>62. 线程池核心参数？★★★</summary>

- corePoolSize 核心线程数、maximumPoolSize 最大线程数、keepAliveTime 空闲存活时间、unit 时间单位、workQueue 任务队列、threadFactory 线程工厂、handler 拒绝策略。
</details>

<details>
<summary>63. 线程池执行流程？★★★</summary>

- 核心线程未满 → 创建核心线程；满了 → 入队；队列满了 → 创建非核心线程到 max；再满 → 走拒绝策略。
- 拒绝策略：AbortPolicy（抛异常）、CallerRunsPolicy（调用者线程执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢最旧任务）。
</details>

<details>
<summary>64. 为什么不建议用 Executors 创建线程池？★★</summary>

- Fixed/Single 用无界队列，任务积压可能 OOM。
- Cached 最大线程数 Integer.MAX_VALUE，线程过多可能 OOM。
- 建议手动 new ThreadPoolExecutor 明确参数。
</details>

<details>
<summary>65. ThreadLocal 原理和内存泄漏？★★★</summary>

- 每个线程有 ThreadLocalMap；key 是 ThreadLocal 弱引用，value 是强引用。
- 线程池复用线程时 key 被回收、value 还在 → 内存泄漏；用完必须 remove()。
</details>

<details>
<summary>66. CountDownLatch / CyclicBarrier / Semaphore？★★</summary>

- CountDownLatch：一次性，主线程等 N 个任务完成。
- CyclicBarrier：可循环复用，N 个线程互相等齐再一起走。
- Semaphore：信号量，控制同时访问的线程数（限流）。
</details>

<details>
<summary>67. 死锁产生的条件？★★★</summary>

- 互斥、持有并等待、不可剥夺、循环等待。
- 预防：破坏其中一个；排查：jstack 看线程栈。
</details>

<details>
<summary>68. 乐观锁和悲观锁？★★</summary>

- 悲观锁：默认会冲突，先加锁（synchronized、Lock、SELECT ... FOR UPDATE）。
- 乐观锁：默认不冲突，更新时校验版本号/CAS；适合读多写少。
</details>

<details>
<summary>69. 并发三大特性？★★★</summary>

- 原子性（synchronized、原子类）、可见性（volatile、锁）、有序性（volatile、锁、happens-before）。
</details>

<details>
<summary>70. happens-before 原则？★★</summary>

- 程序次序规则、锁规则（解锁先于加锁）、volatile 规则（写先于读）、传递性、线程 start/join、中断规则。
- 用来判断数据可见性，满足则无需额外同步。
</details>

## 五、MySQL（71-90）

<details>
<summary>71. 索引为什么用 B+ 树？★★★</summary>

- 树矮胖，3~4 层可存千万级数据，磁盘 IO 少。
- 叶子节点有序链表，范围查询高效；非叶子节点只存索引键。
- 对比：B 树非叶子也存数据更宽；红黑树层数深。
</details>

<details>
<summary>72. 聚簇索引和非聚簇索引？★★★</summary>

- 聚簇（主键）索引：叶子存整行数据，一个表只有一个；主键推荐自增（避免页分裂）。
- 非聚簇（二级）索引：叶子存主键值，查完整数据要回表。
</details>

<details>
<summary>73. 回表和覆盖索引？★★★</summary>

- 回表：二级索引查到主键，再回主键索引取整行。
- 覆盖索引：查询列都在索引中，不用回表（explain 的 Extra 为 Using index）。
</details>

<details>
<summary>74. 最左前缀原则？★★★</summary>

- 联合索引 (a,b,c) 从最左列开始匹配；跳过 a 用 b 会失效。
- 尽量把区分度高的列放前面。
</details>

<details>
<summary>75. 索引失效的场景？★★★</summary>

- 违反最左前缀、对索引列用函数/运算、隐式类型转换、like '%xx'、or 连接非索引列、范围查询后面的列失效。
</details>

<details>
<summary>76. explain 重点看什么？★★★</summary>

- type（const/ref/range/index/all）、key（实际用到的索引）、rows（扫描行数）、Extra（Using index 覆盖索引、Using filesort 排序慢、Using temporary）。
</details>

<details>
<summary>77. 事务的 ACID？★★★</summary>

- 原子性（undo log）、一致性、隔离性（锁 + MVCC）、持久性（redo log）。
</details>

<details>
<summary>78. 隔离级别？★★★</summary>

- 读未提交（脏读）、读已提交（不可重复读）、可重复读（幻读；MySQL 默认）、串行化（全表锁）。
</details>

<details>
<summary>79. MVCC 原理？★★★</summary>

- 隐藏列：trx_id（事务 id）、roll_pointer（指向 undo 版本链）。
- ReadView：活跃事务列表 m_ids、min_trx_id、max_trx_id、creator_trx_id。
- 快照读按版本链找可见版本；RR 复用第一个 ReadView，RC 每次都新建。
</details>

<details>
<summary>80. 当前读和快照读？★★★</summary>

- 快照读：普通 SELECT，走 MVCC，不加锁。
- 当前读：SELECT ... FOR UPDATE / LOCK IN SHARE MODE / UPDATE / DELETE，读最新并加锁。
</details>

<details>
<summary>81. 幻读怎么解决？★★</summary>

- InnoDB RR 下，当前读用 next-key lock（记录锁 + 间隙锁）锁住范围，阻止插入。
- 快照读靠 MVCC 一致性快照。
</details>

<details>
<summary>82. InnoDB 有哪些锁？★★★</summary>

- 行锁（记录锁、间隙锁、临键锁）、表锁、意向锁（IX/IS）、自增锁。
- 只有通过索引定位才走行锁，否则退化为表锁。
</details>

<details>
<summary>83. 死锁怎么排查处理？★★</summary>

- SHOW ENGINE INNODB STATUS 看死锁日志。
- 处理：统一加锁顺序、缩小锁范围、事务尽量短、必要时重试。
</details>

<details>
<summary>84. 慢查询怎么优化？★★★</summary>

- 慢查询日志定位 → explain 分析 → 补索引/修失效/避免 select * → 分页优化（延迟关联）→ 必要时分库分表。
</details>

<details>
<summary>85. redo log 是什么？★★★</summary>

- InnoDB 专用物理日志，WAL（先写日志再写数据），崩溃恢复用，保证持久性。
- 为什么快：顺序写 + 日志比数据页小。
</details>

<details>
<summary>86. undo log 是什么？★★</summary>

- 逻辑日志，记录修改前的状态；用于回滚和 MVCC 版本链。
</details>

<details>
<summary>87. binlog 和 redo log 的区别？★★★</summary>

- binlog：Server 层逻辑日志，主从复制/归档，追加写。
- redo log：InnoDB 层物理日志，崩溃恢复。
</details>

<details>
<summary>88. 两阶段提交是什么？★★</summary>

- 保证 redo 和 binlog 一致：redo prepare → 写 binlog → redo commit。
- 崩溃时按 binlog 是否完整决定提交或回滚，避免主从不一致。
</details>

<details>
<summary>89. 主从复制原理？★★</summary>

- 主库写 binlog → 从库 IO 线程拉取写 relay log → SQL 线程重放。
- 异步/半同步/组复制；延迟问题靠读写分离 + 读从库。
</details>

<details>
<summary>90. 一条 SQL 的执行流程？★★★</summary>

- 连接器（身份校验）→ 分析器（词法/语法）→ 优化器（选索引）→ 执行器（调用存储引擎）→ 返回结果。
</details>

## 六、Redis（91-105）

<details>
<summary>91. Redis 为什么快？★★★</summary>

- 纯内存；单线程避免锁竞争和上下文切换；IO 多路复用（epoll）；高效数据结构。
- 6.0 后多线程只用于网络 IO 读写，命令执行仍单线程。
</details>

<details>
<summary>92. Redis 数据类型？★★★</summary>

- String（缓存/计数）、Hash（对象）、List（队列/栈）、Set（去重/交并差）、ZSet（排行榜，底层跳表）。
- 进阶：Bitmap、HyperLogLog、GEO、Stream。
</details>

<details>
<summary>93. 过期删除策略？★★</summary>

- 惰性删除（读时检查过期）+ 定期删除（随机抽查）。
- 配合内存淘汰策略兜底。
</details>

<details>
<summary>94. 内存淘汰策略？★★</summary>

- volatile-lru / allkeys-lru / volatile-ttl / volatile-random / allkeys-random / noeviction（默认，写报错）。
- 生产常用 allkeys-lru。
</details>

<details>
<summary>95. RDB 和 AOF 持久化？★★★</summary>

- RDB：快照，文件小恢复快，可能丢最后一次快照后的数据。
- AOF：追加命令日志，可配 everysec，丢数据少，文件大；有 AOF 重写。
- 混合持久化：RDB 打底 + AOF 增量。
</details>

<details>
<summary>96. 缓存穿透？★★★</summary>

- 查不存在的数据，每次都打到 DB。解决：缓存空值、布隆过滤器、参数校验。
</details>

<details>
<summary>97. 缓存击穿？★★★</summary>

- 热点 key 过期瞬间大量请求打 DB。解决：互斥锁重建、逻辑过期、热点 key 不过期。
</details>

<details>
<summary>98. 缓存雪崩？★★★</summary>

- 大量 key 同时过期或 Redis 宕机。解决：过期时间加随机值、多级缓存、集群高可用、熔断限流。
</details>

<details>
<summary>99. 缓存和数据库一致性？★★★</summary>

- Cache Aside：先更新 DB 再删缓存，读 miss 再回填。
- 并发问题：延迟双删、binlog 订阅（Canal）、短过期兜底；不要先删缓存再更新 DB。
</details>

<details>
<summary>100. 分布式锁怎么做？★★★</summary>

- SET key value NX EX 原子设置 + 唯一标识防误删；释放用 Lua 脚本（先比对再删）。
- Redisson：看门狗自动续期、可重入。
- 主从切换可能丢锁 → RedLock（复杂，慎用）。
</details>

<details>
<summary>101. 主从/哨兵/集群的区别？★★★</summary>

- 主从：读写分离、数据备份，主挂需手动切换。
- 哨兵：监控 + 自动故障转移，对外仍是单实例。
- Cluster：多主多从分片，数据按 slot 分布，支持水平扩展。
</details>

<details>
<summary>102. 跳跃表是什么？★</summary>

- 多层有序链表，ZSet 底层之一；O(log n) 查找，实现比红黑树简单。
</details>

<details>
<summary>103. 大 key / 热 key 问题？★★</summary>

- 大 key：阻塞、内存不均、删除卡顿 → 拆分、渐进删除。
- 热 key：单节点压力 → 本地缓存、副本分流、随机后缀分散。
</details>

<details>
<summary>104. 布隆过滤器？★</summary>

- 位数组 + 多个 hash 函数；判断「一定不在/可能在」，有误判率，不可删元素。
- 用于防缓存穿透。
</details>

<details>
<summary>105. Redis 事务？★</summary>

- MULTI/EXEC 批量执行，不保证原子性（一条失败不影响其他），无回滚。
- 要原子性用 Lua 脚本（防超卖经典方案）。
</details>

## 七、网络（106-115）

<details>
<summary>106. TCP 三次握手？★★★</summary>

- SYN → SYN+ACK → ACK；确认双方收发能力并同步序列号。
- 为什么不是两次：防止失效的旧连接请求误建立连接。
</details>

<details>
<summary>107. TCP 四次挥手？★★★</summary>

- 主动方 FIN → 被动方 ACK（半关闭）→ 被动方 FIN → 主动方 ACK。
- 为什么四次：半关闭，两端各自关闭数据通道。
- TIME_WAIT：主动关闭方等 2MSL，保证最后一个 ACK 到达且旧报文消失。
</details>

<details>
<summary>108. TCP 和 UDP 的区别？★★★</summary>

- TCP：面向连接、可靠（确认/重传/排序/流量/拥塞控制）、字节流、较慢。
- UDP：无连接、不可靠、报文、快；适合视频/游戏/日志。
</details>

<details>
<summary>109. TCP 怎么保证可靠传输？★★</summary>

- 校验和、序列号、确认应答、超时重传、滑动窗口、拥塞控制（慢启动/拥塞避免/快重传/快恢复）。
</details>

<details>
<summary>110. HTTP 和 HTTPS？★★★</summary>

- HTTPS = HTTP + TLS：对称加密传数据 + 非对称加密交换密钥 + 证书防中间人。
- 握手多 1-2 RTT，性能略低。
</details>

<details>
<summary>111. HTTP 1.0 / 1.1 / 2.0 / 3.0？★★</summary>

- 1.1：持久连接、管线化（有队头阻塞）。
- 2.0：多路复用、二进制分帧、头部压缩；TCP 层仍有队头阻塞。
- 3.0：QUIC（基于 UDP），解决队头阻塞，支持连接迁移。
</details>

<details>
<summary>112. 输入 URL 到页面展示的流程？★★★</summary>

- DNS 解析 → TCP 连接 → TLS 握手（HTTPS）→ 发送 HTTP 请求 → 服务器处理返回 → 浏览器解析 HTML/CSS/JS → 渲染。
</details>

<details>
<summary>113. GET 和 POST 的区别？★★</summary>

- 语义：GET 取数据、幂等、可缓存；POST 提交数据、不幂等。
- 参数：GET 在 URL（有长度限制、会进日志），POST 在 body。
- 底层都是 TCP/HTTP，本质差异在语义。
</details>

<details>
<summary>114. Cookie、Session、Token？★★★</summary>

- Cookie：客户端存储，请求自动带上；HttpOnly 防 XSS 读取。
- Session：服务端存储，靠 sessionId；集群要共享存储。
- JWT/Token：无状态，服务端验签即可；缺点是难以主动失效。
</details>

<details>
<summary>115. TCP 粘包/拆包怎么解决？★</summary>

- TCP 是字节流无边界；解决：定长消息、分隔符、消息头带长度字段（常用）。
- UDP 自带报文边界，无此问题。
</details>

## 八、Spring / Spring Boot（116-130）

<details>
<summary>116. IOC 是什么？★★★</summary>

- 控制反转：对象创建和依赖注入交给容器，解耦。
- DI 方式：构造器（推荐）、setter、字段注入。
</details>

<details>
<summary>117. Bean 生命周期？★★★</summary>

- 实例化 → 属性填充 → Aware 回调 → BeanPostProcessor before → init（InitializingBean/init-method）→ BeanPostProcessor after（AOP 代理在此）→ 使用 → destroy。
</details>

<details>
<summary>118. Bean 作用域？★★</summary>

- singleton（默认）、prototype（每次新实例）、request/session（Web）。
- 注意：单例注入 prototype 会固定；用 ObjectProvider 或 @Scope(proxyMode) 解决。
</details>

<details>
<summary>119. 循环依赖怎么解决？★★★</summary>

- 三级缓存：singletonObjects / earlySingletonObjects / singletonFactories。
- 只能解决单例 + setter 注入；构造器注入无法解决，直接报错。
- 其他思路：@Lazy、重构拆分。
</details>

<details>
<summary>120. AOP 原理？★★★</summary>

- 动态代理：JDK 代理（实现接口）或 CGLIB（子类，Spring Boot 默认）。
- 常用：事务、日志、权限、性能监控。

<details>
<summary>121. Spring 事务传播行为？★★★</summary>

- REQUIRED（默认，有则加入）、REQUIRES_NEW（挂起旧事务开新的）、NESTED（嵌套，Savepoint）、SUPPORTS、NOT_SUPPORTED、MANDATORY、NEVER。
</details>

<details>
<summary>122. 事务失效的场景？★★★</summary>

- 非 public 方法、自调用（this 调用不走代理）、异常被 catch 吞掉、抛 checked 异常（默认不回滚）、类没被 Spring 管理、多线程调用。
</details>

<details>
<summary>123. Spring Boot 自动装配原理？★★★</summary>

- @SpringBootApplication = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan。
- 读取 AutoConfiguration.imports（旧版 spring.factories）→ 条件注解 @ConditionalOnXxx 按需装配。
</details>

<details>
<summary>124. Spring MVC 处理流程？★★★</summary>

- DispatcherServlet → HandlerMapping 找处理器 → HandlerAdapter 调用 Controller → 返回视图或 @ResponseBody 序列化 → 异常处理。
</details>

<details>
<summary>125. Filter 和 Interceptor 的区别？★★★</summary>

- Filter：Servlet 规范，Spring 容器外，作用于所有请求，先执行。
- Interceptor：Spring 容器内，基于 HandlerMapping；preHandle/postHandle/afterCompletion。
- 顺序：Filter → Interceptor → Controller。
</details>

<details>
<summary>126. @Transactional 注意点？★★</summary>

- 默认只回滚 RuntimeException/Error，checked 异常要指定 rollbackFor。
- 必须加在 public 方法，且通过 Spring 代理调用才生效。
</details>

<details>
<summary>127. Spring 中用了哪些设计模式？★★★</summary>

- 单例（Bean）、工厂（BeanFactory）、代理（AOP）、模板（JdbcTemplate）、观察者（事件）、策略（HandlerMapping）、适配器（HandlerAdapter）、装饰器（请求包装）。
</details>

<details>
<summary>128. Spring Boot 比 Spring 多了什么？★★</summary>

- 自动配置、starter 依赖管理、内嵌服务器、actuator 监控、约定大于配置。
</details>

<details>
<summary>129. @Component 系列注解区别？★</summary>

- @Component / @Service / @Repository / @Controller 都是注册 Bean，按分层语义区分。
- @Repository 的异常会转换为 DataAccessException。
</details>

<details>
<summary>130. Spring Boot 常用注解？★★</summary>

- 配置：@Configuration、@Bean、@Value、@ConfigurationProperties。
- Web：@RestController、@RequestMapping、@RequestBody、@PathVariable。
- 声明式：@Transactional、@Cacheable；校验：@Valid / @Validated。
</details>

## 十、项目场景题（141-150）—— 结合你的服装系统

<details>
<summary>141. 讲讲你项目的整体架构？★★★</summary>

- Spring Boot 分层：controller（接口）→ service（业务）→ repository（数据）；dto（入参）/ entity（持久化）/ info（出参）+ converter 转换，实体不直接暴露。
- 模块划分：basic（管理员/员工/仓库/供应商）、product（商品/SKU/选项）、order（收银/进货/调货/盘点）、stock（库存/流水）。
- 统一 Result 返回 + 全局异常处理 + 分页 PageParam/PageResult。
</details>

<details>
<summary>142. 库存超卖怎么解决？★★★</summary>

- 现状：查库存→判断→扣减是读改写，两台收银机并发可能超卖。
- 方案一：SELECT ... FOR UPDATE（@Lock(PESSIMISTIC_WRITE)）串行化同一 SKU 的扣减。
- 方案二：原子 UPDATE SET stock = stock - ? WHERE stock >= ?，按影响行数判断是否扣成功。
- 多实例时可用分布式锁，但数据库始终是最终事实源。
</details>

<details>
<summary>143. 为什么订单金额要后端重算？★★★</summary>

- 单价不信任前端，从 ProductSku 快照取；数量来自前端。
- 总价/实付后端计算并与前端提交值比对，不一致直接拒绝，防篡改。
</details>

<details>
<summary>144. 订单项为什么存快照字段？★★★</summary>

- 商品改名/改价不影响历史订单；存 skuId 弱关联 + productName/skuCode/unitPrice/discount 冗余快照。
- 如果只存 skuId 再 join，历史订单会被改价污染。
</details>

<details>
<summary>145. 你怎么排查和修复 N+1？★★★</summary>

- 现象：列表页每条数据多查一次关联对象。
- 定位：开 show-sql 看日志数 SQL 条数。
- 修复：JPQL JOIN FETCH 一次查出，如 OrderRepository.findPage 直接 fetch employee/wareHouse。
</details>

<details>
<summary>146. JWT 为什么放 Cookie？CSRF 怎么防？★★</summary>

- HttpOnly 防 XSS 读取；SameSite=Lax 限制跨站请求带 Cookie（缓解 CSRF）。
- 生产 Secure=true 只走 HTTPS；前端 withCredentials 带 Cookie。
- 对比 localStorage：JS 可读，XSS 即被盗。
</details>

<details>
<summary>147. 你的权限模型怎么设计的？★★★</summary>

- 两种角色：ADMIN（管理端）、WAREHOUSE（仓库/收银端）。
- 三层：Security URL 规则 + 服务层校验（checkPermission / checkBelongs）+ 前端隐藏入口。
- 仓库只能操作本仓库订单：isCurrentWareHouse 比对当前登录 id。
</details>

<details>
<summary>148. 库存流水怎么设计的？★★</summary>

- StockRecord 反规范化：商品/SKU/仓库编码名称冗余 + 变动前后数量 + 操作人 + sourceNo 溯源。
- 每次库存变动都记流水，可追溯来源（订单号/调货单/盘点单/手动调整）。
</details>

<details>
<summary>149. 订单状态机怎么设计的？★★</summary>

- 收银订单：DRAFT（挂单）→ COMPLETED。
- 进货/调货/盘点：DRAFT → CHECKING → APPROVED / REJECTED。
- 每次流转有状态校验，非法流转抛业务异常；isDraft()/isChecking() 辅助方法。
</details>

<details>
<summary>150. 如果让你设计会员积分，怎么做？★★★</summary>

- 表：会员表（手机号唯一、等级、可用积分、累计积分）+ 积分流水表（收支、来源单号、变动前后）。
- 折扣：等级枚举带 discount 字段，不要只写在注释里。
- 下单：订单快照会员等级和折扣；积分变动走流水，事务内完成。
</details>
